# create-issue — Issue 起票スキル

GitHub Issue を起票するときは**必ず本スキルに従う**。目的は、Claude Code の Auto モードが
**人に質問せず自律的に最後まで遂行できる** Issue を作ること。曖昧さを残さない。

> **Issue の単位は「タスク」**。規模や独立性で分けてよいし、まとめてもよい——**どちらも強制しない／禁止しない**。判断はタスクの実態に委ねる。成果物の中心は**コード＋テスト（What=テスト）**で、設計の方向を決めた判断は **ADR（`docs/adr/`）** に残す（CLAUDE.md の知識配置）。仕様・設計ドキュメントの事前作成は前提にしない。

## 0. 起票の流れ（下書きを先に通す）

Issue はリポジトリを公開すると全部見える。本文を書き直しても前の版は「edited」から読め、タイトルの変更はタイムラインに残る（`docs/adr/0004-treat-as-public-from-day-one.md`）。しかもコミット前の検査は Issue にかからない。そこで**起票する前に、ローカルの下書きでレビューと検査を済ませる**。

1. 下書きを `work/YYYYMMDD/issues/<連番>-<短い名前>.md` に書く（`work/` は gitignore 対象。UTF-8（BOM なし）・改行は LF）。1行目を `# <タイトル>`、2行目を空行、3行目以降を本文（§8 の起動コマンド → §1 のテンプレート）にする。起動コマンドの Issue 番号は `#<N>` のまま置く。
2. `reviewer` に `mode: issue` で下書きを渡す（§7）。`Blocker`/`Major` が無くなるまで下書きを直す。
3. 下書きを検査フックにかける: `sh .githooks/commit-msg <下書きのパス>`。終了コードが 0 でなければ直して 2 からやり直す。表示は「コミットメッセージ:<行>」となるが、行番号は下書きのファイルの行を指す。gitleaks が見つからないと言われたら、環境変数 `GITLEAKS` に実行ファイルを指定する（ルートの README の「コミット前の検査」）。「禁止語の照合ができないため止めます」や Python が無いといった準備不足で止まったときは、下書きを直しても通らない。起票せずに本人に知らせて止まる（`SHIRABE_CHORD_DENYLIST` を差し替えたり、仮のリストを作ったりしない）。
4. 起票する（§6）。出力された番号で下書きの `#<N>` を置き換え、`gh issue edit` で本文を差し替える。
5. 起票した後は、本文・タイトルを書き直さない。直すときは下書きを直して 2・3 を通してから `gh issue edit` する。公開してはいけないものを書いてしまったら、Claude では版を消せないので、すぐ本人に知らせる（本人が「edited」から版を消すか、Issue ごと削除する）。

マイルストーンを新設するときも、タイトルと説明を同じ形でファイルに書き、3 の検査にかけてから作る。

## 1. 本文テンプレート（6項目すべて必須）

下書きの本文は、以下の見出しを省略せず順に書く。**各項目は必要最小限**にする（読む人の負荷を下げるため）。背景は ADR へのリンクで済ませ、完了条件は外形的に判定できる数項目に絞る。ただし、完了条件と判断の既定値は削らない（Auto が迷わないため）。

```markdown
## ゴール

このIssueで達成する状態を1〜2文で。完了が客観的に判定できる表現にする。

## 背景

なぜこのタスクが必要か。関連する **ADR（`docs/adr/`）・既存テスト** があればリンクを張る。
どの GitHub Milestone に属するか（あれば）を1文で書く。

## スコープ

### やること

- 箇条書きで具体的に。対象ファイル・モジュールを名指しする。

### やらないこと

- このIssueで触らない範囲。別Issueに委ねる事項を明記する。

## 影響範囲

- **やった場合の影響**: 変更が及ぶ範囲・他タスクへの波及。
- **放置した場合の影響**: 着手しないと何が滞るか。

## 完了条件

- [ ] チェック可能な条件を列挙（後述の遂行フローを必ず織り込む）。

## 依存Issue

- #<番号>（無ければ「なし」と明記）。
```

### 要確認事項（任意・該当する場合のみ追加）

起票時点で**ユーザー判断が必要だと分かっている分岐**（選択を誤るとスコープや意図から外れ、後戻りが効きにくい事項）があれば、本文に `## 依存Issue` の後ろへ次の見出しを追加し、質問形式で列挙する。無ければこの見出し自体を書かない（曖昧さが無い Issue が基本）。

```markdown
## 要確認事項

- <質問1>（選択肢: A / B。既定案があれば明記）
```

担当エージェントは `work-issue` の着手前スキャンでこの見出しを読み、最初に `AskUserQuestion` でまとめて確認する。

## 2. ラベル（model 必須）＋マイルストーン

`gh issue create --label` に **`model:` を1つ**付ける。

- `model:sonnet` / `model:opus` … 後述の割当指針で選ぶ

関連する開発フェーズを束ねる **GitHub Milestone があれば** `--milestone "<タイトル>"` で割り当てる（任意）。マイルストーン単位で進捗・承認ゲートを回したいときに使う。該当 Milestone が無く新設したいなら、タイトルと説明を §0 の 3 の検査にかけてから `gh api repos/:owner/:repo/milestones -f title="<…>" -f description="<…>"` で作り、割り当てる。単発のバグ修正・小機能などは無割り当てでよい。

## 3. モデル割当指針

**既定は `model:sonnet`**。何をどう作るかは起票の段階（本文の既定値・完了条件）で決め、仕上がりは `reviewer` が点検するので、遂行する側は Sonnet で足りることが多い。

**`model:opus` にするのは、認証情報を使って実際の環境を変える作業を含む Issue だけ**。間違えたときの被害が、手元のコードの修正では済まないため。当たるのは次のとおりで、これで全部とする。

- AWS への `terraform apply`、または AWS のリソースを作る・変える・消すコマンドの実行
- GitHub のリポジトリの設定・Secrets・ブランチ保護の変更、公開・非公開の切り替え
- 上のどちらかで、別の Issue で作った部品を実際の環境でつないで動かすこと

認証情報を使っても、読むだけの作業（`terraform plan`、`aws ... describe`/`list`/`get`、`gh ... view`/`list`）は含まない。Issue の起票・編集・クローズも含まない。それ以外は、調査と ADR、セキュリティや費用の上限に関わるコード、Terraform のコードを書くことも含めて全部 `model:sonnet` にする。当たるか迷ったら `model:sonnet` にし、effort を `high` にする。

## 4. 遂行フロー（完了条件に必ず織り込む）

担当エージェントが自律遂行し、最後に **`reviewer` SubAgent（`mode: artifact`）** のレビューを通す。
**その Issue が実際に作る成果物の項目だけ**を完了条件へ入れる。レビュー項目は必ず入れる。

### コードを実装する場合に入れる項目（基本経路）

- [ ] 追加するコードが既存コード（関数・コンポーネント・共有モジュールなど）で代替できないかを確認した（重複や似た実装があれば再利用・統廃合を優先し、新規追加した場合はその理由を残す）
- [ ] テストを書く前に**テスト項目リスト（テスト名＋日本語説明）を人間に提示し承認を得た**（AutoMode でも必須・実装前の What 合意。不変条件がある対象はプロパティベーステストの要否も検討する）
- [ ] 承認された一覧どおりにテストを先に書き、対象機能を実装した
- [ ] プロジェクトのテストコマンド（CLAUDE.md 記載。未定なら本Issueでは省略可）が**全て通る**

### 設計の方向を決める判断を伴う場合に入れる項目

- [ ] Why / Why not を ADR（`docs/adr/NNNN-内容.md`）に残した

### 必ず入れる項目（レビュー・共通）

- [ ] `reviewer` に `mode: artifact`・Issue番号・**触れた層（docs / code / 両方）** を渡してレビューを依頼した
- [ ] レビューの `Blocker`/`Major` 指摘をメインが対応し、再レビューで合格した

## 5. Auto で迷わせない記述基準

- 「適宜」「必要に応じて」「など」「いい感じに」等の曖昧語を使わない。
- 完了条件は**チェックボックス**で、外形的に真偽が判定できる形にする。
- 対象ファイル・モジュール・参照すべき docs を**パスで名指し**する。
- 判断が要る箇所は、選択肢と既定値を本文に書いておく（実行者に選ばせない）。

## 6. 起票コマンド例

§0 の 2・3 を通した下書きから起票する。タイトルは1行目、本文は3行目以降を渡す。

起票と番号の差し替えは、1回のコマンドでまとめて行う（Bash ツールは呼び出しごとにシェル変数が消えるため）。

```bash
draft=work/YYYYMMDD/issues/01-xxx.md
url=$(tail -n +3 "$draft" | gh issue create \
  --title "$(head -n 1 "$draft" | sed 's/^# //')" \
  --label "model:sonnet" \
  --milestone "<Mn のタイトル>" \
  --body-file -) &&
N=${url##*/} &&
echo "$url" &&
sed -i "s/#<N>/#${N}/" "$draft" &&
tail -n +3 "$draft" | gh issue edit "$N" --body-file -
```

途中で失敗したら、もう一度流す前に `gh issue list` で起票済みかを確かめる（二重に起票しないため）。

## 7. 起票物の検証（reviewer — issue モード・必須）

起票する前に、**`reviewer` SubAgent に `mode: issue` で下書きの検証を依頼する**。これは起票物（ゴールの妥当性・原因分析の前提・スコープ・テンプレ準拠・完了条件のチェック可能性）が的を射ているかを敵対的に点検する工程で、誤った前提のまま実装フェーズに流すのを止めるのが目的。

手順:

1. `reviewer` に `mode: issue`・下書きのパス・検証してほしい観点（本文が主張する原因・前提など、特に裏取りすべき点）を渡す。起票前なので、ラベルとマイルストーンの予定も添える。
2. 判定が **`Blocker` または `Major` を含む**なら下書きを改訂し、**再度 `reviewer`（issue）にかけて「合格（着手可）」になるまで繰り返す**。
3. `Minor` のみ・任意対応で残す場合は、その判断をユーザーへの報告に書いて確定とする。Issue のコメントには書かない（検査を通らない書き込みになるため）。

> `reviewer` がまだ SubAgent として登録されていない場合（定義を作った直後のセッション等）は、`general-purpose` に `.claude/agents/reviewer.md` の観点をそのまま渡して代替実行する。

完了条件への織り込みは**不要**（本検証は起票側＝メインの工程であり、担当エージェントの遂行フローではない）。

## 8. 起動コマンド（Issue 本文の先頭に必ず載せる）

Issue は **Claude が基本対応する**。各 Issue を `work-issue` で自律遂行させる
**`claude` 起動コマンドを本文の最上部（`## ゴール` の前）に必ず載せる**。コピペで起動できる状態にする。

本文先頭は次の形にする（`model`・`level` は下書きで確定する。起票後に埋めるのは `N` だけ）:

````markdown
## 起動コマンド

```
claude --model <model> --permission-mode auto --effort <level> "/work-issue #<N>"
```
````

> `work-issue` は受け渡し（main 直接コミット / worktree+PR）を `CLAUDE.local.md` の運用記載で自動分岐する。起票側でコマンドを使い分ける必要はなく、常に `/work-issue` を載せる。

- `--model`: Issue の `model:` ラベルと一致させる。
- `--permission-mode auto`: AutoMode で自律遂行させる。
- `--effort`: `model:` ラベルを基準に、**タスクの難易度に応じて幅を持たせて**当てる。
  - **sonnet** … 次のどれかを含むなら `high`（これで全部）: ADR を起こす／ログに出すものを決めるコード／訪問者の入力を検証するコード／費用の上限を守るコード／IAM のポリシーや公開範囲を書く Terraform のコード。どれも含まず判断が要るなら `medium`、単純・定型なら `low`。Sonnet は `high` までにする。
  - **opus** … 既定は `high`。複数の Issue の部品を実際の環境で初めてつなぐなら `xhigh`。
- **依存 Issue がある場合**は、コマンドの下に「依存 #M が close 後に起動」と一言添える。

`#<N>` は起票時には未確定なので、下書きには `#<N>` のまま書き、**起票後に発行された番号で本文を差し替える**（§6）。起票後の本文の書き直しは、原則としてこの1回だけにする。

## 9. 仕上げ

依存される側の Issue から順に起票し、後続の下書きの「依存Issue」欄には起票済みの番号を書いてから起票する（起票後に書き足すと本文の版が増える）。番号を書き足しただけなら reviewer は通し直さず、§0 の 3 の検査だけかけ直す。
各 Issue の本文先頭に §8 の起動コマンドが番号入りで入っていることを最後に確認する。
