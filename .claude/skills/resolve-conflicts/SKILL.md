# resolve-conflicts — 軽微コンフリクト解消スキル

複数 PR が並走すると、同じインデックスや追記型ファイルに触れて**機械的なコンフリクト**が起きる。
本スキルは**「両方を残す／重複を消す／並べ直す」だけで正しくなる衝突**に限って自動解消する。
**少しでも意味の判断が要る衝突は解消せず、該当箇所を提示して人間に確認する**（誤マージは静かに壊すため）。

## 1. 自動解消してよいもの / 止めるもの

| 種別 | 例 | 対応 |
| ---- | -- | ---- |
| **追記型ファイルの行衝突** | `docs/discovery/decisions.md` の表、CHANGELOG 等、末尾に行を足すだけのもの | **両方の追記を残す**（union）。重複行は1つに。**append-only の時系列順（日付・新しいものが下 等の既存規約）を保つよう並べ直す**——単純な union で順序が崩れる場合は規約順に直す。 |
| **索引・一覧の重複/順序** | 各種目次、リンク集 | 両者の項目を**統合・重複排除し、既存の並び**に整える。 |
| **import / 列挙の並び** | 名前の列挙リスト等、順序に意味がないもの | 統合して整列。 |
| **コードのロジック衝突** | 同一関数・同一行のロジックが両側で別物 | **解消しない**。両案を提示してユーザーに確認。 |
| **仕様・設計の相反** | 設計文の同一箇所が矛盾する記述に | **解消しない**。矛盾点を提示して確認。 |
| **判断がつかないもの** | union でよいか確信が持てない | **止めて聞く**。 |

原則: **可逆・機械的な衝突だけ自動で。少しでも意味判断が要れば手を止めて確認。**

## 2. 手順

1. **どの作業ツリー・ブランチでコンフリクト中かを最初に確認する**。並列 PR 運用では cwd が main 側か worktree 側かで `git status`/`git add`/`--continue` の効く対象が変わる。`git rev-parse --show-toplevel` と `git status`（rebase 中か merge 中か、コンフリクト中のファイル一覧）を見て、**意図した worktree に居ること**を確かめてから進める。
2. ファイルを開き、`<<<<<<<` / `=======` / `>>>>>>>` の各ハンクを §1 の表で振り分ける。
3. **自動解消対象**だけをその場で直す:
   - 追記型・索引系は両者を統合し、重複排除と規約順の整列を行う。マーカー行（`<<<`等）は必ず全て除去する。
   - 直したファイルは内容を読み返し、両方の変更が正しく残っているか確認する。
4. **止める対象**が1つでもあれば、自動解消を中断し、該当ファイル・ハンクと「なぜ機械的に直せないか」をユーザーに提示して指示を仰ぐ。
5. すべて解消できたら `git add <解消したファイル>` し、`git rebase --continue` / `git merge --continue` を続行する。
6. テストがあるPJなら（プロジェクトのテストコマンド。CLAUDE.md 記載）解消後に再実行し、壊れていないことを確認する。
7. 何をどう統合したか（特に索引の並べ直し）を簡潔に報告する。
8. **rebase 解消後の反映 push は自分で実行しない**。rebase はリモート履歴を書き換えるため反映に `git push --force-with-lease`（強制）が要るが、**この強制 push は破壊的なので Claude は実行せず、実行すべきコマンドをそのまま提示して人間に実行してもらう**（環境によっては force-push が permissions で deny されている）。コンフリクト解消そのもの（手順1〜6）は Claude が行い、最後の強制 push だけ提示にとどめる。通常の（非強制）push も求められたときだけ。

> マーカーの消し忘れ・片側の変更欠落は静かなバグになる。解消後は必ず差分を見返してから add する。
> 強制 push を勝手に走らせない（手順8）。提示したコマンドを人間が実行して初めてリモートへ反映される。
