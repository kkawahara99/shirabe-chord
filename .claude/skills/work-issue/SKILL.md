# work-issue — Issue 遂行スキル

GitHub Issue を1件、原則として自律的に最後まで遂行する。`create-issue` が本文に埋め込んだ
**完了条件と遂行フロー**をそのまま実行する。対象 Issue 番号を受け取って動く。

ただし**情報だけでは正解を選べず、誤るとユーザーの意図やスコープに反する恐れのある分岐**に出くわしたら、
勝手に決めず `AskUserQuestion` でユーザーに確認する（判断基準は「迷ったときの既定」を参照）。
細部の設計判断まで逐一聞くのではなく、後戻りが効かない・方向性を左右する事柄だけに絞る。

## 1. 着手前スキャン（ユーザー判断点の先出し確認）

実装・調査に入る**前**に、ユーザー判断が必要な分岐がないかをまとめて確認する。作業を進めてから判明すると手戻りになるため、ここで前倒しする。

1. Issue 本文に `## 要確認事項` があれば、その質問をそのまま `AskUserQuestion` で確認する。
2. それが無くても、本文・タイトルと関連する **ADR（`docs/adr/`）・既存テスト** を一読し、「後戻りが効きにくく、選択を誤るとスコープ・意図から外れる分岐」が**作業前から見えている**場合は、深く調査せず気づいた範囲でまとめて `AskUserQuestion` で確認する（判断基準は §「迷ったときの既定」と同じ）。
3. ここで聞き漏らした判断点が作業中に新たに見つかった場合は、§「迷ったときの既定」に従いその時点で確認する（再スキャンの往復はしない）。
4. 判断点が無い・1〜2で解決した場合はそのまま §2 へ進む。

## 2. 着手前チェック

1. `gh issue view <N>` で本文・ラベル・完了条件を読む。
2. **依存Issueの確認**: 本文「依存Issue」の各 `#M` が closed か `gh issue view <M> --json state` で確認する。
   - 未完了の依存があれば、その旨を報告して**中止**する（依存先を先に遂行する）。
3. CLAUDE.md の知識配置に従う（[docs/adr/0001-source-of-truth.md](../../../docs/adr/0001-source-of-truth.md)）: **What はテスト・Why は ADR が正本**。仕様・設計ドキュメントの事前存在は前提にしない（無くてよい）。Issue のゴールが何をすべきか（What）を曖昧にしか定めていないなら、不足を報告して確認する。
   - 関連する **ADR（`docs/adr/`）と既存テスト**を先に読み、過去の決定・現在の挙動と矛盾しないか確認する。
4. **既存の決定・挙動と矛盾しないか疑う**: 着手前に、対象が ADR（`docs/adr/`）の既存決定・現在のテストが表す挙動と食い違わないか軽く照合する。食い違いに気づいたら、誤りのまま進めず先に正す（ADR を新規に起こして supersede する／テストを直す）。正し方がスコープ・方向性を左右するなら `AskUserQuestion` で確認してから直す。
5. **運用モードを確認して作業場所を決める**。`CLAUDE.local.md`（git管理外・プロジェクトメモリとして自動読込）の `## 運用モード` にある**「運用」行だけで判定する**（プラン名 Max/Pro 等は判定に使わない）。「運用」行が `PR運用` なら PR運用、それ以外・記載なしは main 直接運用。受け渡し（コミット/PR）の差は §5 にも対応する。
   - **main 直接運用**（既定。「運用」行が無い／`PR運用` 以外のとき） … ブランチ・PR を作らず `main` 上で直接作業する。
   - **PR運用**（「運用」行が `PR運用` のとき） … `main` には直接コミットせず、worktree に feature ブランチを切って作業する:
     - ブランチ名 `<type>/<N>-<短いslug>`（`<type>` は Issue に対応する feat/fix/docs 等、`<N>` は Issue 番号）。
     - **リポジトリ直下を cwd にして** `git worktree add .claude/worktrees/<N>-<slug> -b <branch>`（リポジトリ内に置くことで `.claude/settings.json` の通常の権限設定がそのまま及ぶ。相対パスは cwd 起点。親 `.claude/worktrees/` が無くても git が作る）。
     - **以降の編集・テスト・コミットはすべてこの worktree 内で行う**（main 側チェックアウトを触らない。混同しやすいので `git rev-parse --show-toplevel` でパスを確認する）。
     - push と PR は §5 で行う。

## 3. 遂行（触れる層に応じて）

Issue 本文の完了条件チェックボックスを「やることリスト」として消化する。中心の成果物は**コード＋テスト**。
設計の方向を決める判断をしたら **ADR**（`docs/adr/`）に残す。完了条件・スコープに応じて下記の作業を行う。

### コードを実装する場合（テスト先行・基本経路）

1. **テスト項目リストの人間確認ゲート（AutoMode でも必ず止める・必須）**。テストを書く前に、これから書くテスト項目を一覧で人間に提示し、`AskUserQuestion` で「この What（作るものの振る舞い）で合っているか」を確認する。
   - 一覧は **1項目＝テスト名＋日本語の振る舞い説明** の対で示す。正常系・境界値・異常系を網羅する。
   - 往復一致（parse∘format）・冪等・単調性・範囲・「生成物が常に条件を満たす」等の**不変条件がある対象は、点（例示）だけで済ませず、言語・フレームワークで実用的なら面（プロパティベーステスト）も挙げる**。外部 I/O 結線など面に向かないものは点でよい。
   - **これは仕様書レビューの代わり**。テストが What の正本になる以上、人間が読んで意図を確認する点をここに置く。承認されるまで実装（テスト記述含む）に進まない。指摘があれば一覧を直して再提示する。
   - 承認された一覧が、その Issue の What の基準になる（以降のテスト・実装はこれに沿わせる）。
2. **テストを先に書く**。承認された一覧どおりに、正常系・境界値・異常系を書く（赤）。テスト名は一覧と一致させ、What が読み取れる形を保つ。
3. テストが通る最小実装を書く（緑）→ 重複除去・命名整理（リファクタ）。型・命名で **How** を表現する（説明文書を別置きしない）。
4. プロジェクトのテストコマンド（CLAUDE.md 記載）を実行し、**全テストが通る**ことを確認する。テストコマンドが未定のプロジェクト初期段階では、Issue 完了条件に沿って手動確認の内容を報告に残す。
5. 外部依存（API・CMS・ホスティング等）はラッパ境界に閉じ、上位はモックでテストする。

### 設計の方向を決める判断をした場合（ADR）

- コードにもテストにも表せない **Why / Why not**（外部の癖への対処理由・採らなかった代替案など）が出たら、[docs/adr/](../../../docs/adr/) に `NNNN-内容.md` を1件起こす（`template.md` を複製）。既存決定を覆すなら旧 ADR を `Superseded by NNNN` にする。
- **採番は、すべての worktree とブランチを見て決める**（人には聞かない）。手順は [docs/adr/CLAUDE.md](../../../docs/adr/CLAUDE.md) に従う。
- 一時的な調査・スクラッチは `work/`（gitignore）に置く。

## 4. 敵対レビュー（必須・合格するまで繰り返す）

1. `reviewer` SubAgent を Agent ツールで起動し、**`mode: artifact`・Issue 番号・その Issue が実際に触れた層（docs / code / 両方）** を渡してレビューを依頼する。
2. 返ってきた指摘のうち `Blocker` と `Major` を**メイン（自分）が修正**する（SubAgent は修正しない）。
   - `Minor` は対応するかどうかを Issue 完了条件と照らして判断し、見送る場合は理由を残す。
3. **再レビューは `Blocker`/`Major` を修正したときだけ**行い、**`Blocker`/`Major` ゼロ（合格）** になるまで 2〜3 を繰り返す。
   - `Minor` のみの対応・見送りで終わったなら**再レビューは不要**（そのまま完了処理へ）。
4. コードを実装した Issue では、修正のたびにプロジェクトのテストコマンドが全通過することを再確認する。

> エージェント呼び出しはコストがかかる。**無暗に増やさない**:
>
> - 再レビューは前回指摘の解消確認に絞り、毎回フルレビューを回さない。
> - 可能なら同じレビューSubAgentを継続して文脈（コールドスタート）を再生成しない。継続手段が使えない環境では新規起動でよいが、その分の往復を1回に収めるよう修正をまとめてから依頼する。

## 5. 完了処理

1. Issue 本文の完了条件チェックボックスが**すべて満たされている**ことを自己確認する。
2. **自律判断を残す**: 遂行中に「Issue にも既存の決定にも根拠がなく自分で決めた」判断があれば、重さで振り分ける。
   - **設計の方向を決めた判断（Why / Why not）** → [docs/adr/](../../../docs/adr/) に ADR を起こす（§3「設計の方向を決める判断をした場合」と同じ）。
   - **後から直せる軽微な自律判断** → [docs/discovery/decisions.md](../../../docs/discovery/decisions.md) の表に1行追記する（日付・Issue#・決めたこと・根拠/代替案）。該当が無ければ書かない。
3. **コミットして受け渡す**（§2 項目5 の運用モードで分岐）。メッセージは `commit` スキルの書式（`<type>: <要約>` ＋本文）に従う。**本文は省略しない**——別セッションのClaudeが `git log` だけでこのIssueの経緯（何を・なぜ）を追えるように、Issueのゴールと実際にやったことの要約、関連ADRがあればそのパスを書く。Issue番号は `Closes #<N>`（§下記）で必ず紐づく。`work/`（gitignore）は巻き込まない。コミット末尾のフッタは **モデル名を実際に遂行中のもの**（Issue の `model:` ラベルに対応する haiku/sonnet/opus 等）に合わせる:
   ```
   Co-Authored-By: Claude <実際に使用中のモデル名> <noreply@anthropic.com>
   ```
   - **main 直接運用** … `main` に直接コミットする。コミット末尾に `Closes #<N>` を入れて Issue を自動クローズする。（`Closes` で閉じない場合に備え）`gh issue close <N>` でクローズを確認する。push は求められたときだけ。
   - **PR運用** … worktree の feature ブランチにコミットし、`git push -u origin <branch>` の後 `gh pr create --base main` で PR を出す。**PR は自分でマージしない**（人間ゲート）。本文は下記「PR 本文テンプレ」に従い**3セクションを必ず埋める**。本文に `Closes #<N>` を入れ、マージ時に Issue が自動クローズされるようにする。push/rebase で並走 PR とのコンフリクトが出たら、`decisions.md` の追記行衝突のように両方を残せば済むものだけ解消し（解消後はマーカーの残りを確かめ、テストを流し直す）、ロジックが食い違うものは止めて人間に確認する。**worktree はマージ済みまで残す**（PR レビュー後に人間から修正を求められたら、同じ worktree で追撃修正して再 push するため）。マージは遂行セッションより後の人間ゲートで起きるので、**遂行スキル側では worktree を消さない**——マージ済み worktree／ローカルブランチの回収は SessionStart フック（`.claude/hooks/cleanup-merged-worktrees.sh`：PR が MERGED かつ未コミット変更なしのものだけ remove）が次回以降のセッション起動時に自動で行う。リモートのマージ済みブランチは GitHub の head ブランチ自動削除設定に任せる。
4. **マイルストーン承認ゲート**: 本 Issue の Milestone の状態を `gh issue list --milestone "<タイトル>" --state open`（必要なら `--state closed` も）で確認する。
   - **main 直接運用** … 本 Issue は既に closed 済み。他に open が残っていなければ、これがマイルストーン最後の Issue。
   - **PR運用** … 本 Issue は PR マージまで open に残るため open 件数だけでは判定できない。**本 Issue を除いた他の Issue**で振り分ける: ①他に作業中（PR 未作成）の open が残る→まだ最後ではない。②他がすべて closed→このPRのマージでマイルストーン完了（到達はマージ時に確定）。③他に未マージ PR（open）がある→複数の最終PRが並走しうるので到達宣言はしない。代わりに PR 本文へ「他に未マージPRがあるM<n>。最後にマージされるPRで人間が到達ダイジェストを確認すること」と書き残し、宙吊りを防ぐ。
   - **最後の Issue だと判定した場合**は、**勝手に次のマイルストーンへ進まない**。`decisions.md` にそのマイルストーン分の判断を `=== <マイルストーン名> 到達ダイジェスト ===` 見出しでまとめ、「マイルストーン到達ダイジェスト」（下記）を報告して**人間の承認を待つ**（PR運用ならその内容を **PR 本文の冒頭**にも「⚠️ これがマイルストーン最後の Issue。本PRマージで到達」と明示して載せる）。承認は人間が口頭／PR マージで行う。
5. 完了を報告する。報告には**「認識ずれ想定」を必ず1項目入れる**——根拠はあるが人間の意図・期待と食い違うかもしれない箇所（解釈の仮置き・TBDの埋め方・想定ユースケースの取り方など）を「ここは合っていますか？」と問う形で挙げる。**無ければ「なし」と明記する**（`decisions.md` の「根拠なく決めたこと」とは別の、前向きな疑いの早期共有）。PR運用なら**作成した PR の URL** も伝える。未解決で残した `Minor` 指摘があれば理由とともに伝える。

### PR 本文テンプレ（PR運用時・人間ゲートの認知負荷を下げる3セクション）

非エンジニアの意思決定者が PR を読んで「マージしてよいか」を最小の負荷で判断できるよう、コードの細部ではなく**決定と疑い**を見せる。3セクションは省略せず、該当が無ければ「なし」と明記する。各項目は1〜2文、全体で読んで1分以内に収める。

```markdown
Closes #<N>

## 概要（意思決定者向け）
専門用語を避け、平易な言葉で次の3点をそれぞれ1〜3文でかみ砕いて書く。
- **何ができるようになったか**: このPRで利用者から見て何ができる／何が変わるか。
- **なぜ必要か**: それがないと何に困るか、何のための変更か。
- **リスク**: マージで起こりうる悪影響・不確実な点（影響範囲、未検証の箇所、後戻りのしやすさなど）。無ければ「なし」。

## Claude が自律判断したこと
仕様・設計・Issue に根拠がなく自分で決めた点を箇条書き（`decisions.md` の該当行に対応）。各項目に「なぜそう決めたか」を一言添える。なければ「なし」。

## 認識齟齬が疑われる項目
根拠はあるが人間の意図・期待と食い違うかもしれない箇所を「ここは合っていますか？」形式で。解釈の仮置き・TBDの埋め方・想定ユースケースの取り方など。なければ「なし」。

## 完了条件 / テスト
- Issue の完了条件チェックボックスの充足状況
- コードを実装した Issue ならテスト結果（全通過の事実）
```

### マイルストーン到達ダイジェスト（人間の承認用・差分ではなく決定を見せる）

マイルストーン最後の Issue を仕上げたら、コードのdiffではなく**人間が方針ズレを判断できる情報だけ**を簡潔に報告する（PR運用ではPR本文にも載せる）:

- **達成状態の充足**: このマイルストーンのゴール（GitHub Milestone の説明／Issue 群）を満たしたか（満たした根拠を1〜2文）。
- **勝手に決めたこと**: このマイルストーンで自律判断した点（重い判断は ADR、軽微は `decisions.md` の該当行）。「ここは合っていますか？」と問う形で。
- **想定とずれうる点 / TBD**: 未確定をどう仮置きしたか、人間の意図と食い違いそうな箇所。
- **次のマイルストーン**: 次に進むマイルストーンと、その着手にあたり先に確認したいこと。

この報告でユーザーが承認したら次のマイルストーンの Issue 着手に進む。

## 迷ったときの既定

判断に迷ったら、まず **ADR（`docs/adr/`）・既存テスト** と Issue 本文を再確認する。それでも決まらないとき、次で振り分ける。

- **自律で進める（質問しない）**: 既存の決定（ADR）・テストが表す挙動・外部様式に沿えば一意に決まる細部、後から直せる軽微な選択。最も単純で既存の決定に沿う案を採り、判断内容をコミット/報告（重ければ ADR）に残す。
- **`AskUserQuestion` で確認する**: どこにも根拠がなく、**選択を誤るとユーザーの意図やスコープから外れ、後戻りが効きにくい**分岐。例) スコープの解釈が複数あり成果物の形が変わる / 未決事項を実装で固定してしまう / 既存の決定（ADR）と衝突しうる。**加えて次は AutoMode でも必ず止めて確認する（軽微に見えても例外なく）: コードを書く Issue の「テスト項目リスト」確認ゲート（§3・実装前の What 合意）。** 聞くときは選択肢と各々の影響を簡潔に示す。
- **作業を中止する**: 依存Issue未完了、または Issue のゴール（What）が曖昧で何をすべきか定まらない。理由を報告して止まる。

迷ったら「**後戻りの効きやすさ**」で測る。すぐ直せるなら進め、方向性を固定してしまうなら聞く。質問の濫発もコスト。本当に意図を左右する分岐だけに絞る。
