# 0030. 費用のアラートを bootstrap に置き、メールの通知だけに留める

- **Status**: Active
- **Date**: 2026-11-07

## Context

サイトは公開済みで、アクセスが増えた分はそのまま費用になるが、今は請求まで気づけない。費用はほぼゼロの想定（[0006](0006-product-scope-and-stages.md)）なので、止める仕組みでなく、気づく仕組みだけを足す。

宛先のメールアドレスは公開しない（[0004](0004-treat-as-public-from-day-one.md)）。置き場所によっては、CI のロールが読める状態ファイルに入る。

AWS の文書で次を確かめた（2026-11-07）。

- メールの宛先には検証メールが送られ、検証した宛先にだけ通知が届く。宛先の人がこのアカウントにサインインして完了させ、リンクの期限は 12 時間。同じアカウントで検証済みの宛先なら、検証メールなしで有効になる。API で作った宛先の初期状態は文書に書かれておらず、未確認（[メールの宛先](https://docs.aws.amazon.com/cost-management/latest/userguide/budgets-email-recipients.html)）。文書の状態の名前（`Active` など）とコンソールの表示（`Verified`）は違う。
- 予算の情報の更新は 1 日に最大 3 回で、前の更新から通常 8〜12 時間空く。利用から請求までの遅れもあるので、通知より先に費用が予算を超えることがある（[予算の管理](https://docs.aws.amazon.com/cost-management/latest/userguide/budgets-managing-costs.html)）。実績の通知は、予算の期間で 1 回だけ送られる（[ベストプラクティス](https://docs.aws.amazon.com/cost-management/latest/userguide/budgets-best-practices.html)）。
- 費用の種類（`cost_types`）の既定では、税・サブスクリプション・サポート・前払いと定期の予約の料金・割引・返金・クレジットをすべて含み、ブレンド料金と償却の料金は使わない（[CostTypes](https://docs.aws.amazon.com/aws-cost-management/latest/APIReference/API_budgets_CostTypes.html)）。

## Decision

- `infra/bootstrap/budget.tf` に `aws_budgets_budget` を 1 つ作る。`COST`・`MONTHLY`・`USD` で、絞り込みを付けずアカウント全体を見る。`cost_types` は既定のまま使う。
- 通知は `ACTUAL` が予算の 80% と 100% を超えたときの 2 つで、宛先はメール 1 件だけにする。
- `budget_alert_email` は既定なしの必須の変数で、`sensitive = true` にする。実値は `terraform.tfvars`（gitignore 対象）に書く。
- `monthly_budget_usd` は既定 2 の変数で、額はここだけで管理する。
- 適用の後、宛先の検証が済んだことをコンソールで確かめる（手順は `infra/bootstrap/README.md`）。

## Consequences

- 宛先は bootstrap の状態ファイルに平文で入る。この状態ファイルは手元のローカルにあり、S3 に置かないので、CI のロールは読めない。秘密の値を状態ファイルに載せない決まり（[0003](0003-account-agnostic.md)）は、状態ファイルを読めるロールが秘密まで読めることを避けるためのもので、その懸念はここでは起きない。
- 変数が必須なので、適用済みの人は `terraform.tfvars` に宛先を足す必要がある。
- Budgets を SCP（組織で一律にかけるアクセス制限）で拒否するアカウントでは、bootstrap の適用が失敗する。そのアカウントでは、予算の定義（`budget.tf`）を手元で外すなどの対応が要る。
- 額や宛先を変えるときは適用し直す。bootstrap は「初回だけ」が基本だが、予算を変えるときは例外になる。
- 検証が済むまで通知は届かない。適用しただけでは、気づく仕組みは完成しない。
- 通知は最大で半日以上遅れうるので、費用が急に増えたときの被害を防ぐものではない。
- 既定の費用にはクレジットが含まれる。文書は既定値までしか述べていないが、クレジットで相殺されている間は費用が低く見え、通知が出ない可能性がある。

## Why not

- **本体のルートモジュール（`infra/app/`）に置く**: PR 用ロールが読める状態ファイルに宛先が入る。両方のロールに `budgets:` の権限が要り、宛先を Secrets で CI に渡すことにもなる。
- **別のルートモジュールを作る**: リソース 1 つのために、状態ファイルと適用の手順が増える。bootstrap には、手で適用する流れとローカルの状態ファイルがすでにある。
- **宛先を任意の変数にする**: 書き忘れると、誰にも届かない予算が黙ってできる。作らない分岐も要る。SCP で拒否されるアカウントは少数と見て、失敗で気づける形を採る。
- **額をパラメータストアに置く**: 額は秘密でなく、結局 Terraform で読んで適用するので、置き場所が増えるだけになる。
- **額を Budgets のコンソールで変える**: コードと実態がずれ、次の適用で元の額に戻る。差分を無視する設定（`ignore_changes`）で許すと、コードから額が読めなくなる。
- **費用が増えたら自動で止める（Budgets のアクション）**: 公開サイトが止まる害のほうが、想定の費用より大きい。
- **WAF を付ける**: Web ACL だけで月 5 USD かかり（確認時点の料金）、予算の 2 USD を超える。
- **予測の通知（`FORECASTED`）を足す**: 予測には約 5 週間の利用データが要り、費用がほぼゼロのうちは役に立ちにくい。実績の 80% で早めに気づける。
