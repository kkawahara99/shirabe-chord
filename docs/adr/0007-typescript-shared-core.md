# 0007. 実装は TypeScript とし、ブラウザとサーバーで同じコア（コード理論と最適化）を使う

- **Status**: Active
- **Date**: 2026-11-03

## Context

押さえ方を探すコアは、ブラウザの中で動かしたい（サーバー費をかけず、入力への反応を速くするため）。一方、掲載（[0006](0006-product-scope-and-stages.md) のモード 3）では、クライアントから送られた押さえ方を、サーバーでも検証する必要がある。コアを 2 つの言語で書くと、検証が食い違う。

## Decision

- 実装言語は TypeScript。サイト（ブラウザ）と、サーバー側の処理（AWS Lambda、Node.js のランタイム）のどちらも同じ言語で書く。
- コード理論（コード記号 → 構成音）、押さえ方の候補の生成、最適化、構成音の検証は、DOM や AWS に触れない純粋な関数として 1 か所に置き、ブラウザとサーバーの両方から使う。
- コアのテストは、決まった入力に決まった出力が返ることを確かめる。性質（生成された押さえ方が、必ず必要な構成音を含む、など）は、プロパティベーステストでも確かめる。

## Consequences

- コアの検証ロジックが 1 つになり、クライアントとサーバーで食い違わない。
- Lambda の依存に npm のパッケージが入りうる。供給網攻撃への備え（版の固定、ロックファイル、依存を最小にする）を、実装の Issue で決める。
- Python で書いた検査フック（`.githooks/`・`.claude/hooks/`）は、そのまま残す。アプリのコードとは別。

## Why not

- **Python で書き、サーバーだけで最適化する**: 入力のたびにサーバーを呼ぶことになり、費用と遅延が増え、ブラウザだけで動く（[0006](0006-product-scope-and-stages.md) のモード 1・2）設計にできない。
- **ブラウザは TypeScript、サーバーは Python で、同じアルゴリズムを 2 回書く**: 検証が食い違い、保守も二重になる。
