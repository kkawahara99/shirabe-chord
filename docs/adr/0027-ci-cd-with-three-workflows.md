# 0027. CI/CD を「テスト・PR の plan・main のデプロイ」の 3 本に分け、危険なトリガーは「使ってよい一覧」で縛る

- **Status**: Active
- **Date**: 2026-11-07

## Context

[0003](0003-account-agnostic.md) で、GitHub Actions は OIDC で AWS に入り、アカウントIDは伏せ字にし、接続先は Secrets で渡すと決めた。ロールの信頼ポリシーは、リポジトリと ref（main か PR か）までしか見ない（#40）。そのため、main の上で動くワークフローは、イベントの種類を問わず同じ `sub` になる。誰でも起こせるイベント（`issues`・`pull_request_target`・`workflow_run`・`fork` など）は多く、禁止の一覧では抜けが出る。

実行ログは公開後に誰でも読める。plan と apply の出力にはアカウントIDの入ったバケット名が出うる（[0005](0005-resource-naming.md)）。

## Decision

- ワークフローは 3 本に分ける。
  - `test.yml`: `pull_request` と `workflow_call`。AWS には入らない。main への `push` は付けず、`deploy.yml` が呼ぶ。
  - `plan.yml`: `pull_request`。同じリポジトリの PR だけで動かし、PR 用ロールで `terraform plan` を流す。出力はジョブのログにだけ出す。
  - `deploy.yml`: main への `push` だけ。`test.yml` を呼び、通ったら 1 つのジョブで `terraform apply`、サイトの配置、キャッシュの削除を行う。
- PR では apply しない。反映は main へのマージ後だけにする。
- 接続先（状態ファイルのバケット、ロールの ARN、リージョン）は GitHub Secrets で渡し、Variables は使わない。Secrets は `run:` に埋めず `env:` で渡す。`run:` に `${{ github.event.* }}` も埋めない（シェルへの注入を避けるため）。
- AWS に入るジョブは `plan.yml` と `deploy.yml` に 1 つずつにし、`id-token: write` はそのジョブだけが持つ。伏せ字の設定（`mask-aws-account-id`）はジョブ単位で効くので、AWS の手順は 1 ジョブにまとめる。`deploy.yml` の出力の取り出しと配置も同じステップに置き、バケット名とディストリビューション ID は `::add-mask::` で伏せてから使う。
- サードパーティのアクション（`actions/` 配下を含む）は、コミット SHA で固定し、版をコメントで添える。固定する版は、GitHub が記録する公開時刻（`releases` の `published_at`）から 7 日以上たったものにする。コミット日は作った側が自由に書けるので使わない（[0015](0015-pnpm-workspace-and-dependency-guards.md) と同じ考え方）。
- Terraform は `terraform_version` を完全に固定し、ラッパーを切る（ラッパーが標準出力に行を足し、`terraform output -raw` の値を壊すため）。
- 安全の条件は `.github/tests/test_workflows.py` で守る。トリガーは「ファイルごとに使ってよいもの」の一覧で縛り、参照してよいロールの Secrets もファイルごとに 1 つに限る。

## Consequences

- 同じリポジトリの PR では、PR 側で書き換えた `plan.yml` がそのまま動く。そのため書き込み権限を持つ人に対する守りは、ワークフローのテストではなく、ロールの信頼ポリシーと PR 用ロールの権限（読み取りとロックの書き込みだけ）である。ワークフローのテストが守るのは、うっかりと、書き込み権限のない人の経路。
- Secrets が無いうちは、main への push のたびに `deploy.yml` の AWS に入る手順が失敗する。実環境の準備と動作確認は M2 の最後の Issue で行う。
- アクションの版を上げるときは、公開から 7 日待ち、タグが指すコミットが固定する SHA と一致することを確かめ直す。
- デプロイのジョブは、依存のインストールとビルドの間も OIDC のトークンを取れる状態にある（AWS に入る手順を 1 ジョブにまとめ、伏せ字を効かせるため）。ビルドが乗っ取られれば配る成果物も汚せるので、増える被害は小さいと見て受け入れる。
- 同時実行の制御（`concurrency`）は、待ちを 1 つしか持たない。続けて main に入ると、途中の push のデプロイは飛ばされ、最後の push のデプロイだけが走る（最新の main に揃うので許す）。
- Terraform の接続先とリージョンを環境ごとに変える場合や、独自ドメインの変数の CI への渡し方は、この決定に含めない（独自ドメインに切り替える Issue で決める）。

## Why not

- **plan の結果を PR にコメントする**: バケット名のアカウントIDが、伏せ字なしで PR に残る。コメントは編集・削除しても履歴やキャッシュに残りうる。
- **`pull_request_target` で fork の PR にも plan を出す**: 信頼できないコードが Secrets と OIDC の権限つきで動く。
- **`workflow_dispatch` で手動デプロイを足す**: 書き込み権限のある人が、レビューを通さずに好きなときに apply を起こせる。入口が増えるほど、使ってよいトリガーの一覧と、そのテストの対象が増える。デプロイの入口は main へのマージ 1 つに絞る。
- **environment で承認を挟む**: 承認する人が作者ひとりで、自分で承認するだけでは守りにならない。信頼ポリシーも `sub` を `environment` に変えることになり、PR 用ロールとの切り分けが増える。
- **危険なトリガーの禁止一覧で守る**: 新しいイベントが増えたとき、一覧から漏れる。
- **アクションをタグで指す**: タグは付け替えられ、乗っ取られたアカウントから悪意ある版が同じタグで配られうる。
- **1 つのワークフローにまとめる**: PR の plan と main の apply で必要な権限が違い、トリガーの一覧で縛れない。
