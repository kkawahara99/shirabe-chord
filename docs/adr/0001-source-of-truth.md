# 0001. 正本をコード＋テスト＋ADR に置く（仕様・設計を正本としない）

- **Status**: Active
- **Date**: 2026-11-03

## Context

本プロジェクト（shirabe-chord）は、コード進行に沿ったギターの押さえ方を出力するサイトを、AWS上に構築・運用するポートフォリオである。構成方針や実装の細部は自分たちで決めるものであり、外部から与えられた固定契約仕様ではない。

手書きの自然言語ドキュメント（仕様書・設計書）はコード変更で自動更新されず、書いた瞬間から腐る。AIコーディングエージェントが古い仕様書を読んで古い実装をする事故も起きやすい。知識は「自動で腐らない形」に置くべき、という考え方を採る。

## Decision

知識を性質ごとに配置し、それぞれの置き場所を正本とする。

| 知識 | 正本 |
| --- | --- |
| How（どう動くか） | コード本体（型・命名・ユビキタス言語） |
| What（何をすべきか） | テスト（挙動を表す名前＋可能ならプロパティベーステスト） |
| Why / Why not（なぜ決めた／採らなかった） | ADR（`docs/adr/`・イミュータブル追記・supersede） |

- 内部の仕様書・設計書を正本として新規に書き起こさない。初期構築時の指標として一時的な設計メモを書くこと自体は禁止しないが、正本にはしない。
- 人が全体像を見たいときは構成図等を**コードから都度生成する**（コミットしない）。
- 暫定スコープ・進捗は GitHub Issues / Milestones で扱う。
- 設計の方向を決めた判断の**正式な記録は ADR**。決定が変わったら新しい ADR で supersede する（旧ADRは書き換えない）。

## Consequences

- ドキュメントの二重管理と腐敗を避けられる。AIが古い仕様に引きずられる事故を防げる。
- 公開リポジトリとして読まれたとき、設計判断の理由と却下した案が ADR から辿れる。
- 軽微な自律判断ログ（`docs/discovery/decisions.md`）は履歴として残すが、設計級のWhyはADRに書く。

## Why not

- **仕様・設計を正本として維持する**: コード変更で自動更新されず腐る。外部契約仕様でもないため固定の必然がなく却下。
- **ドキュメントを全廃しコードのみにする**: Why / Why not はコードから導出できず失われる。ADRは残す。
