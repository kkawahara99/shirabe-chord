# 0018. 押さえ方の並びは、単体と移動のコストの合計が最小になるものを動的計画法で選ぶ

- **Status**: Active
- **Date**: 2026-11-04

## Context

[0006](0006-product-scope-and-stages.md) は、コストが最小になる並びを動的計画法で選ぶと決めたが、コストの項目と重み、入力の上限は決めていない。重みは音楽的な判断を含み、ギター担当の修正結果で後から調整する前提である。

## Decision

- 並びのコストは、選んだ押さえ方ごとの単体コストの合計と、隣り合う押さえ方の移動コストの合計。重みは `DEFAULT_COST_WEIGHTS`（`cost.ts`）の 1 か所に置く。
  - 単体: 指の数 1・セーハの有無 0.5・押さえる幅 0.3・押さえる位置の平均フレット 0.2 を足し、開放弦 1 本につき 0.5 を引き、ミュートの弦 1 本につき 2 を足す。
  - 移動: 平均フレットの差の絶対値に 0.6、押さえ方が変わる弦 1 本につき 0.4 を足す。平均には開放弦とミュートの弦を入れない。押さえるフレットが無い押さえ方の位置は 0（開放の位置）とする。
- 初期値は、`C Am F G` と `Dm7 G7 CM7` で定番の押さえ方（`x32010`・`x02210`・`133211`・`320003` など）が選ばれるように、試作で絞った（`progression.test.ts` の代表の進行）。
- 各コードの候補を層とし、前から最小コストを積み、後ろからたどる（`selectCheapestPath`）。コストが同じなら候補の順序で先を選ぶ。最後のコードから後ろ向きにたどるので、最小の並びが複数あるときは、後ろのコードの順序が優先される。浮動小数点の誤差だけの差は同点とみなす。
- 入力は 1000 文字・64 コードまで。超えたら失敗にする（`optimizeProgression`）。区切る前に全角を半角にそろえる（NFKC）。
- ミュートの項目は Issue の項目に無かったが足した。足さないと、F が `1 0 x 2 x x` のような 3 本だけの薄い押さえ方になる（開放弦の値引きと指の少なさだけで安くなるため）。

## Consequences

- 重みを変えると、代表の進行の期待値も変わる。ギター担当の修正結果を見て調整する。
- 64 コードの処理時間は、重い記号だけを並べた最悪ケースで 1 秒を超えることを受け入れた（大半は押さえ方の候補の生成の時間）。画面側で、読み込み中の表示と、計算で画面が固まらない工夫をする。
- 押さえるフレットが無い押さえ方の位置を 0 に決めたのは、移動の距離を三角不等式を満たすものにするため。位置を「無し」として差を 0 にすると、その押さえ方を挟んだとき、同じコードが続くのに違う押さえ方が選ばれることがあった。
- 弦をまたぐ指の動き、リズム、指の太さは扱わない。

## Why not

- **前から 1 つずつ一番近いものを選ぶ（貪欲法）**: 後ろのコードのために前の押さえ方を変える方が楽な場合を逃す（`cheapest-path.test.ts` に例がある）。
- **AI モデルで選ぶ**: [0006](0006-product-scope-and-stages.md) の Why not のとおり。
- **押さえるフレットが無い押さえ方との位置の差を 0 とする**: 上のとおり、距離の性質が崩れ、同じコードが続いても押さえ方が変わる。
- **ミュートの項目を足さずに、開放弦の値引きを小さくして抑える**: 開放弦の値引きを下げると、開放弦を使う定番の押さえ方まで不利になる。
