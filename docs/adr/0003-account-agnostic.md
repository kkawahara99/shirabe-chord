# 0003. Organizationsに依存せず、単独のアカウントでもランディングゾーン内でも動かす

- **Status**: Active
- **Date**: 2026-11-03

## Context

本プロジェクトは公開リポジトリとして、誰かが自分の単独のAWSアカウント（Organizations に属さないアカウント）で試せる形にしたい。一方で作者自身は、Organizations で管理されたマルチアカウント環境（ランディングゾーン）の1アカウントに置いて運用する。ランディングゾーン側のコードは公開しない。

両方で動かすには、次の2つが要る。

- アカウントの外側（Organizations、SCP＝組織で一律にかけるアクセス制限、別アカウントのDNSなど）を前提にしないこと。
- ランディングゾーン側が先に用意しているかもしれないリソースと、衝突しないこと。

公開リポジトリでは、GitHub Actions の実行ログも誰でも読める。GitHub の Variables に入れた値は、ログで伏せ字にされない。

## Decision

- 本体のルートモジュールは Organizations のデータやAPIを参照しない。認証は実行環境のプロファイルから取る。アカウントIDやARNは、手元では変数（`*.tfvars`、gitignore対象）で、GitHub Actions では Secrets で渡す。
- `bootstrap/` は、初回だけ手で適用する準備用のルートモジュールとする。状態ファイル用のS3バケット、GitHub Actions 用の OIDC プロバイダ（GitHub が発行するIDトークンをAWSに信頼させる仕組み）、デプロイ用のロールを作る。
- `bootstrap/` は、OIDC プロバイダを「新しく作る」か「既存のものを使う」かを変数で選べるようにする。OIDC プロバイダは、1アカウントに同じURLで1つしか作れないため。
- デプロイ用のロールは、信頼の条件を「このリポジトリの main ブランチ（または指定した環境）」に限る。PR で差分を確認するときは、別の読み取り専用のロールを使う。ただし状態ファイルのロック用オブジェクトの書き込みだけは許す。
- GitHub Actions でAWSの認証情報を取得するときは、アカウントIDを伏せ字にする設定を明示的に有効にする。
- 秘密の値（ボット対策の秘密鍵など）は Terraform の外で SSM パラメータストアに入れ、状態ファイルに載せない。状態ファイルを読めるロールが秘密まで読めることを避けるため。
- ランディングゾーン側が受け持つのは、次の3つだけとする。このリポジトリはそれらを前提にしない。
  - アカウントの払い出し
  - 人のアクセス権
  - 独自ドメインを使う場合の、サブドメインの委任

## Consequences

- 単独のアカウントでも、準備用のルートモジュールを適用してから本体を適用すれば動く。
- README の前提条件に、次の点を書く必要がある。
  - リージョンを制限するSCPがあると、CloudFront の証明書を置くバージニア北部リージョン（`us-east-1`）が拒否されうる。
  - 新しいアカウントでは、利用枠（クォータ）が低いことや、一部のサービスが使えないことがある。
- ランディングゾーン側で共通のガードレール（監査ログ、GuardDuty など）が入っていても、このリポジトリはそれを当てにしない。

## Why not

- **ランディングゾーンのコードから、払い出したアカウントの中身まで作る**: 公開リポジトリだけで完結しなくなり、他の人が試せない。
- **OIDC プロバイダを常に新しく作る**: ランディングゾーン側で同じプロバイダが作られている場合に、衝突して失敗する。
- **OIDC を使わず、アクセスキーを GitHub に登録する**: 長期の鍵が漏れたときの被害が大きく、公開リポジトリの見本として示せない。
- **アカウントIDやロールのARNを GitHub の Variables で渡す**: 公開後の実行ログに伏せ字なしで出る。
