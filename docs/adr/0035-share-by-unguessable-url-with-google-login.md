# 0035. 譜面の共有を、URL を知る人だけが見られる形にし、ログインは Google だけにする

- **Status**: Active
- **Date**: 2026-11-07

## Context

[0006](0006-product-scope-and-stages.md) のモード 3 は「恒久的に掲載し、コメントを残せる」だった。用途は、作曲者がギター担当へ譜面を渡すこと。公開のポータルより、URL を知る人だけが見られる共有のほうが合い、連絡は LINE などで足りるのでコメントは要らない。ユーザー情報はなるべく持たない。

## Decision

0006 と [0008](0008-aws-managed-services-for-mode3.md) は書き換えず、次のとおり改める（0024・0032・0033 と同じ扱いで、両者の Status は触らない）。0006 のモード 3 のうち、掲載とコメントを本 ADR の共有に置き換える。0008 の部品の選定（DynamoDB・Cognito・API Gateway・Lambda）は有効で、コメントの分だけ使わない。

**共有の性質**

- 共有は「URL を知る人だけが見られる」。公開の一覧・検索・コメントは作らない（本人が自分の共有を見る `/mine` だけ置く）。共有ページと API の応答に `X-Robots-Tag: noindex` を付け、検索エンジンに載せない。運営者が他人の共有を消す仕組みは作らない（必要になったら DynamoDB の項目を手で消す）。
- 共有 ID は、128 ビット以上の乱数を URL に使える文字列にしたもの。推測できないことだけで閲覧を守る。
- 1 人 20 件まで。件数の確認と書き込みの間に並行して作られ、20 を少し超えることは許容する。期限切れは設けず、本人が削除するまで残す。
- 1 件の上限は、タイトル 50 字、ひと言 200 字、表示名 20 字（コードポイント単位）、コード数は `MAX_PROGRESSION_CHORDS`。

**ログインと個人情報**

- ログインは Google のみ。Google から受け取る範囲は `openid` だけで、メール・名前の属性を持たない（Cognito には `sub` と、IdP の識別子の属性は残る）。
- 共有ページの表示名は、共有のたびに本人が入力する任意の文字列（空なら「匿名」）で、アカウントと結びつけない。閲覧の応答に所有者の識別子（`sub`）を含めない。

**保存するもの**

- 各コードの内部の記号と最終の押さえ方、カポ、タイトル・ひと言・表示名、作成日時。固定（ピン）の情報は保存しない。
- DynamoDB はテーブル 1 つ。主キーは共有 ID。所有者（`sub`）の索引（並びのキーは作成日時。ID・タイトル・作成日時・コード数を写す）で、一覧と件数を引く。
- 作成は、ログイン済み・Turnstile の検証・構成音の検証（サーバー側。カポは 0028 のとおり形の記号にしてから検証する）を通ったものだけ受け付ける。

**画面と配置**

- 共有ページの URL は `/s/<ID>`、自分の共有の一覧は `/mine`、ログイン・ログアウト後に戻る先は `/`。API は同じドメインの `/api/` 以下に置く（CORS を使わない）。
- Lambda の実行ロールは `infra/bootstrap` で、Google のクライアント ID の設定にかかわらず固定の名前で作る（IAM ロールは無料で、使われなければ何も起きない）。デプロイ用ロールには、IAM については、そのロールを渡す権限（`iam:PassRole`）だけを与える。デプロイ用ロールが強いロールを作って権限を広げられないようにするため。
- 共有の部品（`infra/app` の Cognito・API・DynamoDB など。上の実行ロールを除く）は、Google のクライアント ID が設定されたときだけ作る。未設定のあいだは、これまでどおり静的サイトだけが配られ、画面に共有のボタンは出ない。

**既存の ADR との食い違い**

- [0028](0028-capo-as-transposition.md)（カポを保存しない）→ 共有ではカポを保存する。
- [0033](0033-pins-follow-chords-and-reset-on-symbol-or-capo-change.md)（固定を保存・共有する仕組みは無い）→ 共有は固定ではなく、押さえ方そのものを保存する。固定の仕組みは変えない。
- 0006（入力文字はタイトルとコメントに限る）→ タイトル・ひと言・表示名に改める。
- [0003](0003-account-agnostic.md)（秘密の値は Terraform の外で SSM に入れ、状態ファイルに載せない）→ Google のクライアントシークレットだけは例外として、状態ファイルに入れる。理由は Consequences に書く。

## Consequences

- 共有 ID を知る人は誰でも見られる。URL が漏れたら止められず、本人が削除するまで有効なままになる。
- 運営者が中身を見て消す手間は、手作業に寄せる。荒らしは、ログイン・Turnstile・件数の上限・API のスロットリングで防ぐ。
- 保存するのは押さえ方そのものなので、後でコアの最適化が変わっても、共有した譜面は変わらない。
- アカウントに結びつけて持つ属性は `sub` と IdP（外部のログイン提供元。ここでは Google）の識別子だけで、表示名は共有に付く文字列にすぎない。ログに残る通信元の IP アドレスや、利用者が自分で書く文字までは、この決定では防げない。入力文字（タイトル・ひと言・表示名）は信用できないデータとして、表示を無害化する。
- Google のクライアントシークレットは、Cognito の IdP の設定の引数に要るので、Terraform の変数として状態ファイルに入る。一方、Turnstile の秘密鍵は実行時に Lambda が読むだけなので、SSM に手で作り、状態ファイルに入れない。差が出るのは、前者は Terraform が値を要求し避けられず、後者は避けられるから。状態ファイルの保管先を守ることが、前者の前提になる。
- 件数の上限は並行して作られると少し超える。厳密にするには条件付き書き込みやカウンタの項目が要り、20 件の目安にそこまで要らない。
- 配信のヘッダ（CSP。[0023](0023-static-site-delivery-with-cloudfront-and-s3.md)）は、Turnstile の読み込みと Cognito への通信を許すよう見直しが要る。`/s/<ID>`・`/mine` は `index.html` に振り分ける設定が要る。実行ロールを足すので、既存の環境は `infra/bootstrap` を手で再適用する（0003）。
- 共有を使わない人は、Google のクライアント ID を設定しなければ、アプリ側の部品も費用も増えない（[0003](0003-account-agnostic.md) のとおり単独のアカウントで試せる）。

## Why not

- **公開のポータル（一覧・検索・恒久的な掲載）**: 荒らしや無害化、運営者による削除など守りが重くなる。用途は特定の相手への受け渡しで、見つけてもらう必要がない。
- **進行を URL に詰める方式**: ログインも DB も要らないが、押さえ方まで入れると URL が長くなり、LINE などで崩れやすい。件数の管理や削除もできない。
- **メールやパスワードのログイン**: メールアドレスやパスワードの保管・再設定を持つことになる。Google の `openid` だけなら、個人情報を持たずに本人の識別ができる。
- **コメント**: 連絡は LINE などで足りる。書き込みの無害化と荒らし対策が増える。
- **進行だけを保存し、押さえ方は開くたびに計算する**: コアの最適化が変わると、渡した譜面が変わってしまう。サーバーでの検証も、保存した押さえ方に対して一度で済む。
- **共有 ID に連番や短い文字列を使う**: 推測されると、閲覧を守るものがなくなる。
- **運営者向けの削除画面や通報の仕組み**: 利用者が少ないうちは、項目を手で消せば足りる。必要になったら新しい ADR で足す。
