# 0002. IaC（インフラのコード化）ツールにTerraformを採用する

- **Status**: Active
- **Date**: 2026-11-03

## Context

本プロジェクトのAWSリソース（静的サイトの配信、API、データの保存、認証、費用の監視など）はコードで管理する。このリポジトリは公開し、単独のAWSアカウントでも、マルチアカウント環境の1アカウントでも、同じコードで構築できることを目指す（[0003](0003-account-agnostic.md)）。

そのため、対象アカウントに前提の仕込みを要求しにくいこと、振る舞いをテストで表せることが、ツール選定の条件になる。候補として Terraform、AWS CDK、AWS SAM を比べた。

## Decision

IaCツールに Terraform（AWSプロバイダ）を採用する。振る舞いは `terraform test`（`.tftest.hcl`）で検証する。

## Consequences

- 状態ファイル（tfstate）の置き場所を自分で用意する必要がある。置き場所の作成は初回だけ手で行う別のルートモジュールに分ける（[0003](0003-account-agnostic.md)）。
- 変数の検証（`validation`）とテストで、不正な入力を `plan` より前に弾ける。
- AWS以外のサービス（ボット対策など）を後から足すときも、同じツールのプロバイダで書ける。

## Why not

- **AWS CDK**: 対象アカウントごとに事前の準備（`cdk bootstrap` による専用のスタック・バケット・ロール）が要り、「単独のアカウントにそのまま入れられる」という目標に一手間増える。
- **AWS SAM**: Lambda周りは簡潔に書けるが、CloudFrontや費用の監視などサーバーレス以外のリソースは素のCloudFormationに戻り、利点が薄い。
